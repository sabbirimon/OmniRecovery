# System architecture

Status: proposed Phase 0 design. Requirements in this document define acceptance criteria for future implementations.

## 1. Components and privileges

| Component | Authority | Boundary |
| --- | --- | --- |
| CLI, desktop UI, lab UI | Authenticated requests and case-scoped views | Clients cannot open acquisition devices, decrypt vault objects directly or bypass policy |
| Case service | Identity, authorization, jobs, durable operation state and audit sequencing | Owns the policy boundary for every client and rechecks it at effect time |
| Acquisition broker | One approved source handle and a bounded read method | Short-lived privileged helper. Device protocol verbs and IOCTLs are allowlisted. It never takes a shell command, generic IOCTL, or write handle |
| Vault service | Encrypt, verify and persist objects and custody records | Per-tenant storage and keys. Workers receive bounded read sessions rather than key material or vault paths |
| Worker supervisor | Schedule, cancel and isolate parsing, decoding and model tasks | No ambient network, raw device access, other case visibility or direct write into the vault |
| Export and retention service | Deliver approved packages, place holds and enforce disposition | Approved destinations and release policy are checked at commit. Separate maintenance role and process for destructive hardware actions |
| Integrity verifier | Verify evidence manifests, journal, signer history and checkpoints | Independently runnable and able to check an externally supplied trust root and checkpoint |

The initial trust boundary is a memory-safe Rust service with a CLI over local IPC. Use Unix domain sockets with peer credentials or Windows named pipes with explicit security descriptors and peer identity, plus application MFA for human sessions. Define protocol version and framing independently of UI code. Lab access terminates at an authenticated gateway with a distinct network-facing process. Client identity is bound to an authenticated session. Tenant and user identifiers supplied in request bodies carry no authority.

SQLite is the case catalogue and operation ledger. In a lab the service hosts each tenant database on supported local storage and brokers all access. Clients never share or mount the database. Evidence objects use immutable filesystem storage with tested durability semantics. Start with a single active ledger writer per tenant. High availability and clustered write fencing require a separate design and failover tests. See the [architecture decisions](decisions.md).

## 2. Acquisition and write-blocking

1. Create a case with a scoped authority record, owner, classification, retention policy, and authorized operators. Record device identifiers, operator notes and photographs as restricted records. Capture the examiner's method and the expected effects of that method.
2. Enumerate source metadata without acquiring content. Resolve stable device identity, media size, geometry, partition ancestry and write-blocker details. Resolve the destination to its backing storage. Disallow overlap and block acquisition when the relevant storage topology cannot be proven. Inspect automount state and qualify the full OS, bridge and device path for physical acquisition. The source stays open through the approved session and is rechecked after reconnect.
3. Bind the approvals to the source identity and geometry, the acquisition method and scope, the destination, the policy version, and the expiry. Recheck source identity against the opened handle immediately before reading. Resolve destinations relative to a trusted opened directory and reject symlinks, reparse points and path substitution. The CLI never accepts a raw destination device in the acquisition path.
4. Open source media read-only. Raw-device capture adds a qualified hardware write blocker where required by the deployment. USB transport and read-only descriptors do not prove that firmware or a running mobile OS leaves all state untouched. Label live ADB, MTP and iOS backup methods as logical acquisitions and log observed effects, consent prompts and known possible mutations. Preserve acquisitions as separate objects when method or source state changes.
5. Stream with bounded memory, checkpointed ranges and deterministic output ordering. Phase 1 regular-file input must be immutable under a supported snapshot or controlled input procedure. Check source identity, size and available change metadata before and after reading and before resume. Resume proves that committed ranges still match the source or uses a previously attested immutable snapshot. If a failing source cannot be safely reread or its identity is ambiguous, stop automatic resume and retain the partial result.
6. A bad-sector map records exact ranges, attempts, error classes and retry policy. A complete raw output can have a source-stream digest and independently verified stored digest. A partial acquisition records a digest over the authenticated range manifest and the bytes actually read. A raw interoperability image with zero-fill is a derivative with its own digest and mandatory hole map. Its manifest cannot present it as an exact clone. Files recovered across unreadable or ciphertext regions are marked partial or excluded with an explicit reason.
7. Reopen and verify persisted data before committing the acquisition. Verify signed manifests and authenticated chunks again as later stages consume bytes, and rehash full objects during scheduled scrubs and before release. A mismatch quarantines the object, blocks downstream use and creates an auditable incident. Report UTC time with source and uncertainty. Use signed local time evidence or an attended clock procedure in the air gap and a deployment-approved time source in the lab. Sequence numbers record order when clock confidence is degraded.

FAT, NTFS and other filesystem repairs use a copy-on-write overlay or create a distinct derivative with provenance. Raw cloning to a physical destination is a later, separately approved workflow with a purpose-bound write handle. It shares no source or command path with acquisition. [SWGDE acquisition practices](https://www.swgde.org/documents/published-complete-listing/17-f-002-2-1/), [SWGDE mobile evidence practices](https://www.swgde.org/documents/published-complete-listing/18-f-003-2/)

For multi-terabyte sources, acquisition uses a bounded read, hash, encrypt and persist pipeline. The destination applies backpressure before further reads. Raw-device jobs start with sequential reads and a device-specific retry budget. Additional passes target unread ranges under the approved policy. Preserve progress by extent and mark the job incomplete when cancellation or media failure prevents coverage. Recovery workers can process bounded image ranges in parallel, but the merge uses fixed ordering by source, extent, method and candidate digest. Keep memory use independent of image size by using disk-backed indexes and quotas on candidate count and temporary storage.

## 3. Vault, custody and crash recovery

- **Objects.** Address evidence by SHA-256 and length inside an encrypted, tenant- and case-scoped index. Physical storage names are opaque. An object manifest binds tenant, case, object ID, byte count, chunk layout, acquisition geometry, unreadable-range map and plaintext digests. Cross-tenant and cross-case deduplication is disabled. An examiner can compare hashes inside an authorized case. Optional SHA-1 and MD5 interoperability digests are labeled legacy and may be unavailable under a strict provider policy. SHA-256 governs integrity and identifiers.
- **Encryption.** Use AES-256-GCM with a fresh data-encryption key and unique nonce per chunk under that key. Allocate a monotonically increasing chunk counter within documented provider invocation limits. Resumed writes produce fresh encrypted segments under fresh data keys, including when a crash leaves uncertain state. Authenticate identifiers, format version, segment and chunk indices and lengths as associated data. Bind the ordered segments and expected total length in the authenticated manifest. Authenticate each chunk before releasing it to a reader. Reject truncation, reordering and cross-case substitution.
- **Commit protocol.** Stage encrypted data privately, flush it, publish immutable files atomically on the same volume and make their directory entries durable. Commit object references, job state and the signed custody event in one SQLite transaction after publication. Readers only see committed references. Crash reconciliation can verify or quarantine an orphan. It may reclaim incomplete staging data only after checking its lease and retention state and recording the outcome. Restore tests cover the entire database, objects, receipts and checkpoint lineage together.
- **Custody.** The ledger appends a signed, versioned event for each security-relevant operation and transition. Each event records tenant, case, sequence, prior hash, authenticated actor, human sponsor when delegated, operation digest, decision, policy version, time source and result code. The signing format uses deterministic CBOR with fixed field rules, domain separation and algorithm identifiers. The verifier rejects duplicate map keys and noncanonical encodings. Approval assertions are recorded with the operation. Restricted details stay encrypted outside the public event envelope. Audit access, administration, policy changes, denials, integrity checks and verifier results also receive events. Unauthenticated attempts carry an explicit unauthenticated status and bounded request context. High-volume reads can be represented by a job-scoped signed access manifest.
- **Rollback defense.** Send signed checkpoints to an independently controlled witness. In a strict air gap, a witness can use controlled removable media and an independent offline verifier that keeps its own durable latest head. Verify against the last trusted checkpoint before sensitive operations and anchor the intent before effects. Require the witness receipt to bind the requested ledger head, sequence, prior witnessed head and a fresh challenge. Mark stale, divergent or missing checkpoints explicitly. A valid chain by itself proves continuity within the observed prefix. A restore that would lose witnessed history requires a controlled recovery ceremony and a new linked ledger epoch. The witness detects competing heads and tracks freshness. High-assurance write, export and deletion paths stop if the configured required witness is unavailable.
- **External effects.** Reserve an operation ID, atomically consume its approvals and record the intent before external effects. Use idempotency keys bound to request content. Stage approved exports as encrypted packages with signed manifests, then publish only within a registered destination. Log delivery attempts and receipts. If a crash leaves the result uncertain, mark it for reconciliation and block automatic repeat. Destructive effects follow the same durable intent rule with additional reconciliation, destination identification and independent verification.

Reserve audit capacity separately from job staging space and deny new effects when required audit writes cannot be made durable. Verify a restored copy against the independently held checkpoint and its backups before enabling sensitive actions. If previously witnessed records cannot be recovered, document the exact known gap and recovery authority in the new linked epoch. The verifier reports the discontinuity. Generate case-specific release manifests and attestations so ordinary exports do not expose unrelated case activity from a tenant ledger.

[RFC 8949 deterministic encoding](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2)

## 4. Identity, two-person integrity and handling policy

| Role | Intended permissions |
| --- | --- |
| Administrator | Enroll identities, manage deployment configuration and update trust roots under ceremony. No evidence read permission by role alone |
| Examiner | Open assigned cases, record authorization, request acquisition, run recovery and propose export |
| Reviewer | Review methodology and findings in assigned cases and approve eligible operations within assigned authority |
| Auditor | Inspect scoped custody records, checkpoints and control evidence. Evidence bytes require a separate grant |
| Read-only | View explicitly released, case-scoped findings at the required classification |

High-assurance enrollment binds one named human principal to independently verified identity and hardware-backed factors. Require PIN or biometric user verification with an approved FIDO2 authenticator or PIV/CAC challenge-response with locally provisioned trust and revocation material. WebAuthn requires an explicitly provisioned relying party and validated origin, RP ID and user-verification flag. Use the PIV/CAC path for the first strict offline pilot. Validate a native FIDO2 path separately before enabling it on a network-denied field kit. Initial enrollment, identity recovery, role grants affecting approval, audit trust changes and privileged policy changes require controlled administrative ceremonies. Log revocation, require freshness according to local policy and invalidate outstanding grants on credential or role revocation.

Each sensitive action requires a requester and independent approver who are distinct people and hold the required case permissions. Two tokens or accounts for one person cannot satisfy the policy. Approvals bind tenant, case, canonical operation digest, data scope, destination or device, effect limits, policy version, expiry and single-use nonce. Show the human the exact action in a trusted interface. Recheck role membership, token status, scope, current retention and classification at effect time. Untrusted clock or expired revocation material blocks sensitive actions until resolved under deployment procedure.

The handling policy labels source objects, jobs, derivatives, model inputs and outputs. Derivatives inherit the highest sensitivity and combined caveats unless an authorized review explicitly releases a separately identified redacted derivative. Exports require a compatible registered route, recipient, package encryption and dual approval. Expiry makes a case eligible for disposition review. A legal hold blocks deletion, key destruction and storage lifecycle policies across live storage, replicas and backups. Recheck at the serialized destruction boundary. Evidence retention, audit retention and object garbage collection have separate policies. Hold removal and any governance exceptions are attributable and independently approved. [NIST SP 800-63B-4](https://csrc.nist.gov/pubs/sp/800/63/b/4/final), [WebAuthn](https://www.w3.org/TR/webauthn/)

## 5. Keys and deployment profiles

The provider boundary supplies authenticated encryption, secure random generation, key wrap, signing, verification and the approved TLS implementation. Use tenant- and case-scoped encryption key hierarchies and purpose-separated signing keys. Prefer an HSM or customer-managed provider for evidence keys. TPMs and smartcards can hold compatible keys and protect local identity or key release. Normal key rotation rewraps data keys with a new versioned key-encryption key. Suspected data-key compromise requires re-encryption under new keys with explicit custody linkage. Preserve historic public keys, trust history and verification policies. Cryptographic erasure is eligible only when approved policy can account for every affected key copy, escrow, replica, export and backup. Failed or unverifiable destruction yields an incomplete disposition record.

Keep secrets out of logs, command-line arguments, environment variables, model context and crash reports. Use bounded, short-lived secret buffers with explicit zeroization, guarded OS facilities where available, disabled crash dumps and controlled swap and hibernation. Validate the actual provider's memory behavior and hardware key export policy. A strict FIPS configuration pins the CMVP certificate, exact module version and operating environment, enforces the applicable approved services and fails closed if initialization or policy checks fail. No generic provider fallback is available in that configuration. Long-lived formats allow a policy to require both an approved classical signature and an ML-DSA signature once supported by the selected provider. ML-KEM is reserved for approved hybrid key establishment. Bind the algorithm suite to the signed context and reject downgrade. [CMVP validated modules](https://csrc.nist.gov/Projects/Cryptographic-Module-Validation-Program/Validated-Modules), [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final), [FIPS 204](https://csrc.nist.gov/pubs/fips/204/final)

| Profile | Proposed operational boundary |
| --- | --- |
| Standalone air gap | OS denies IP socket use, including loopback, for the product and its workers. Use local IPC, offline trust and revocation bundles, offline license verification if required, and signed updates on controlled media. No DNS, time sync, cloud inference or telemetry calls |
| Field kit | Standalone controls on a signed, read-only boot image with writable encrypted destination and documented Secure Boot, automount, USB and storage policy. The chosen hardware, blocker and recovery procedure must be qualified |
| Isolated lab | Dedicated TLS 1.3 with mTLS on an allowlisted private segment. Explicit tenant isolation in process credentials, storage, keys, queues and logs. Allowlisted offline or private dependencies with egress denied by default. Dedicated instances for deployments that require stronger isolation |

Air-gap and lab builds have distinct configuration and distribution manifests. Signed updates bind the package digests, target profile, version and minimum supported release. Validate signatures and rollback state before activation. Rehearse offline recovery from a failed update using approved media. Licensing status cannot lock an authorized verifier out of preserved evidence. Harden a specific supported OS image against selected DISA STIG and CIS baseline revisions and record justified deviations. [TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html), [DISA STIGs](https://public.cyber.mil/stigs/), [CIS Benchmarks](https://www.cisecurity.org/cis-benchmarks)
